# Planit

Web 版 OmniPlan —— 以**依赖驱动排期**为核心的甘特图项目管理工具。
改任何一个任务、依赖、日历或资源，整条链路自动重排；关键路径实时高亮；
资源超载自动平衡；所有操作可撤销。数据存于浏览器，无需服务端。

## 功能详解

### 任务与排期

- **任务树**：摘要任务 / 子任务 / 里程碑三级结构；摘要任务日期自底向上自动汇总；类型（是否有子任务）由结构自动同步，不会出现「有子任务却还是叶子」的脏数据
- **两种排期方式**：
  - **自动**——引擎按依赖与约束求解。可挂**成对的开始 / 结束约束**（开始不早于 / 开始不晚于 / 结束不早于 / 结束不晚于），每个任务 start、end 各一条
  - **手动**——区间直接钉死，不被依赖、约束或资源平衡移动；依赖顶住它时如实报告冲突而不是挪动它
- **每个任务可独立设置**尽早（ASAP）/ 尽晚（ALAP）；项目整体可正向排（从起点推）或逆向排（从截止日倒推，无截止日时退回正向完成日）
- **拖拽排期**：拖动任务条即可平移、拉左把手改开始日、拉右把手改工期；落点自动吸附到工作日；拖拽落下的任务转为手动排期，所见即所得
- **里程碑**：零工期的时间点，可挂依赖、可被平衡推迟

### 依赖

- **四种依赖类型**：FS（完成→开始）/ SS（开始→开始）/ FF（完成→完成）/ SF（开始→完成），甘特图上从任务条端点直接拖出连线即可建立
- **延迟（lag）三种单位**：工作日 / 自然日（跨周末与节假日）/ 前置任务工期的百分比；均可为负（提前量）
- 依赖成环在建立时即被拒绝（环检测），不会等到求解才炸
- 依赖不可行时（如被手动排期顶住）在冲突列表如实报告，绝不静默调和

### CPM 引擎与关键路径

- 完整的**关键路径法（CPM）**求解：正推（最早日期）、逆推（最晚日期）、总浮时 / 自由宽延
- **改任何东西全链自动重排**：任务工期、依赖、约束、日历、资源分配，任何一处变化都触发重求解
- **关键路径实时高亮**：零浮时任务链在甘特图上一眼可辨
- 冲突（负浮时）如实报告为不可行排期，并给出差多少个工作日
- 求解跑在 **Web Worker** 上：10,000 任务的项目求解期间界面保持 60fps，状态栏有「计算中」指示器（延迟 300ms 出现，避免闪烁）

### 工作日历

- 每个项目自带**可配置工作日历**：周工作日勾选 + 任意日期的节假日例外
- 例外可按**单日或区间**增删（区间在命令层自动逐日展开，撤销一次全回）
- **月度日历视图**：工作日 / 非工作日 / 例外日三态着色，点选日期即可切换
- 资源可挂**独立日历**（`calendarId`），也可用项目默认日历
- 改日历立即全盘重算——所有排期、负载、挣值跟着动

### 资源与工作量

- **四种资源类型**：人员 / 设备 / 材料 / 分组（分组可嵌套，面板上按组折叠）
- 每资源可配：**可用率**（如半职 50%）、**效率**、**可用期间**（入职 / 租期）、**成本**（每次使用 + 每小时费率）
- **分配**有两个对称入口：任务面板「这个任务用了谁」、资源面板「这个人被派到哪些任务」——同一份数据、同一套命令，改哪边都一样
- **两种投入模型**：
  - 固定工期：多派一个人，工作量增加、工期不变
  - **固定工作量**：多派一个人，工期真的会缩短（如 5 人日派 2 人 → 3 个工作日）
- 大纲与面板显示每个任务 / 每个资源的派生总量：总使用次数、总时数、总成本

### 资源平衡

- 同一资源同一天被排到超过 100% 可用率时，引擎自动**用浮时把任务往后推**，直到负载回到 100% 或浮时耗尽
- **优先级决定谁先被推**：优先级数值大的任务先占用资源；被钉死的（手动排期 / 约束）任务不动
- 手动指定 `delay`（至少推迟量）会被遵守（夹到浮时上限内）
- **无法消除的超载如实报告**（哪个人、哪天、负载多少），不谎报「已平衡」
- 资源视图的时间线上**超载高亮**，一眼看出谁在哪天被排爆
- 平衡只是普通命令——**可以撤销**

### 基线与挣值（EVA）

- **多基线快照**：随时给全项目拍快照、可存多份、随时切换对比哪份
- **排期差异**：每任务显示基线开始 / 结束与当前排期的工作日差（正数 = 落后）
- **挣值**：BAC（完工预算）/ EV（挣值）/ PV（计划值）/ SV（进度差异）由引擎从成本与进度统一派生，UI 不自行计算
- 设了 `statusDate`（基准日）+ 有活动基线即可计算 PV / SV

### 视图

- **甘特视图**：任务条、依赖连线（四种类型的端点语义）、关键路径高亮、非工作日底纹、拖拽排期
- **大纲视图**：表格化的任务树，**27 列注册表**（开始 / 结束 / 浮时 / 已分配 / 成本 / 差异……），列头右键菜单配置可见性，列宽拖拽调整、双击复位、偏好持久化
- **日历视图** / **资源视图**：与甘特 / 大纲组成四段切换器
- **Inspector 双 Tab**（任务 / 项目）：任务信息、排期、约束、依赖、分配、基线、挣值，7 个可折叠分组

### 数据、撤销与国际化

- **命令模型**：所有数据变更的唯一入口是命令；UI 只 dispatch，不直接改数据
- **完整撤销 / 重做**：Immer 自动生成正向与逆向 patch，双栈回放；拖拽一次 = 一条撤销记录（不会退半步）
- **自动存盘**：IndexedDB 防抖落盘，刷新不丢；schema 版本**逐跳迁移**，旧存档永远可打开
- **三语界面**：中文 / English / 日本語，随时切换；所有文案（含撤销提示）完整翻译

## 开发

```bash
pnpm install
pnpm dev        # 开发服务器（端口 5174；Playwright e2e 同端口）
pnpm test       # 单元测试（vitest）
pnpm typecheck  # 类型检查
pnpm build      # 生产构建
pnpm e2e        # 端到端验收（Playwright，需先 pnpm exec playwright install chromium）
```

`scripts/` 是开发辅助脚本，不进构建产物：

- `seedLargeProject.ts` —— 生成 1000 任务的压测项目（`perf.spec.ts` 用）。
- `importOmniPlan.py` —— 把真实 OmniPlan 文档（`.oplx`）转成 planit 的
  `Project` JSON（`schemaVersion` 与当前 `SCHEMA_VERSION` 一致），
  用于拿真实数据实测排期引擎。纯标准库、无依赖：

  ```bash
  python3 scripts/importOmniPlan.py path/to/xxx.oplx -o out.json
  ```

  导入是**单向且有损**的：OmniPlan 的资源平衡结果 `leveled-start` 不会带过来，
  planit 会用自己的 CPM + leveling 重算 —— 两边日期的差异正是实测要观察的东西。

## 架构

```
View  (React + Mantine)    ← 只 dispatch 命令，不直接写 store
  ↓
Command (命令注册表)        ← 所有数据变更的唯一入口
  ↓
Store  (Zustand + Immer)   ← 命令 + 正/逆向 patch 双栈
  ↓
Domain (纯 TypeScript)     ← 模型 / 日历 / CPM 求解，零 React 依赖
  ↓
Persist (IndexedDB)        ← 防抖自动存盘
```

调度引擎（`src/domain/scheduler`）是纯函数，可脱离 UI 单独测试 ——
排期正确性由单元测试保证，UI 只需验证「操作后数据对不对」。
重求解在 Web Worker 中异步执行，主线程只做渲染。

引擎与 OmniPlan 4 的**规则对齐**（依赖换算、约束语义、资源平衡）以
真实 `.oplx` 文档的整数天 / 无争用子集做 parity 回归（`src/domain/scheduler/omniplan/`）。

## 关于 UI 层的两个约定

**Mantine 与自研的边界**：工具栏、表单、弹层、布局原语用 Mantine；
甘特图区域（刻度尺、网格、任务条、依赖连线、任务树行）自研，
用 SCSS Modules + 绝对定位 + SVG。这些区域需要像素级控制和虚拟滚动，
组件库会碍事。

**i18n**：所有用户可见文案都走 `t()`。命令的 `label` 字段存的是 i18n key
（如 `commands.task.create`），UI 渲染撤销提示时才翻译 ——
这样命令层保持语言无关。

## 端到端验收（e2e/）

前一阶段的 UI 验收是临时的 `browser_evaluate` 断言，验完即弃、没有回归保护。
`e2e/` 把它们固化成了可重跑的 Playwright 测试：

- `regression.spec.ts` —— 6 类曾经真实发生过的微妙缺陷（左右行对齐、
  sticky 左列钉住、连接柄/把手可点、依赖连线端点、拖拽中 store 不变、
  底纹跟随日历）。每条都用**独立于实现**的期望值（DOM 几何或手算日期），
  且已用「重新引入缺陷」的方式验证过确实会变红。
- `acceptance.spec.ts` —— 设计文档的验收标准中可自动化的部分。
- `perf.spec.ts` —— 大项目压测（滚动帧率、改日历同步阻塞）。
- `known-limitations.spec.ts` —— 「已知限制」的表征测试，修好后会立刻变红。

```bash
pnpm e2e                                  # 全部
pnpm e2e regression.spec.ts               # 只跑回归
pnpm e2e -g "底纹跟随用户日历"             # 按标题过滤
```

## 已知限制

> **注意**：本节的三条限制都有对应的表征测试。
> 修复其中任何一条时，请同步删除该测试与本节对应条目 —— 否则测试会变红而你需要知道那是**预期的**。

以下三条均经实测（`e2e/perf.spec.ts` 与 `e2e/known-limitations.spec.ts`
可复现），属有意保留、未处理的问题。

### 1. 大项目下改动工作历时的重渲染卡顿

**求解本身已不再是瓶颈**：引擎跑在 Web Worker 上，10k 计划下主线程阻塞从
797ms 降到 ~40ms，求解期间界面保持 60fps（见 ROADMAP「排期引擎性能」）。

**剩下的卡顿在重渲染，而且只在改动工作历时出现**（10,000 任务，生产构建实测）：

| 操作 | 主线程最大帧间隔 |
|---|---|
| 改任务名（不触发时间轴重建） | **17ms** ✅ |
| **改工作日历**（甘特重建时间轴 + 底纹） | **300ms** ❌ |

原因（1000 任务档的分解，本机 headless Chromium 实测）：

| 部分 | 耗时 |
|---|---|
| `solve()` 纯求解 | ≈ 16ms |
| store 侧同步更新 + 强制回流 | ≈ 17ms |
| **其余 ≈ 190ms：`ProjectView` 的重渲染** | |
| ↳ 其中非工作日底纹一节 | ≈ 97ms |
| ↳ 其余（全量行的几何 memo + 时间轴） | ≈ 97ms |

这条 1000 节点长链把时间轴拉到约 4200 天，光是「非工作日底纹」就产生
**1200 个 DOM 节点**——把日历临时改成「每天都是工作日」后，阻塞立刻降到
≈ 113ms。store 侧本身很轻（solve 十几毫秒）。

**结论**：属已知性能天花板，未优化。后续方向：底纹改为 canvas /
单层渐变、`rectByTaskId` 与时间轴按可见范围分片、长链场景下调 `overscan`。

> 早前另一次基准（不同机器 / 项目形状）测得 1000 任务约 114ms、2000 任务约
> 215ms。绝对数字随机器与时间轴跨度变化，量级为**数百毫秒**。
>
> ⚠️ 量这块**必须用生产构建**：React 开发版的开销在万级规模下能占掉渲染时间的
> 一大半（同一操作 dev 实测 746ms vs 生产 17ms），拿 dev 数字会导向错误的优化方向。

### 2. 早于项目起点的排期会画到时间轴原点左侧

当手动排期或负延迟使任务的开始日期**早于 `project.startDate`** 时，
它的任务条会落到时间轴原点左侧（`left` 为负），被 sticky 左列盖住。

例：项目起点 `2026-03-02`，某任务工期 3、手动钉在 `2026-03-03` 结束，
反推开始日为 `2026-02-27` —— 比原点早 3 个自然日，任务条画在 `x = -96px`。

这是**预存在**的行为：时间轴原点固定为 `project.startDate`，任何排期早于
项目起点的任务都会被盖住。`e2e/known-limitations.spec.ts` 固化了当前行为作为证据。

### 3. 列宽不支持键盘调整

大纲视图的列宽只能靠鼠标 / 触控拖动表头分隔线调整，双击可复位单列，
但没有任何键盘入口（手柄是 `role="separator"` 的 `div`，没有 `tabindex`）。
宽度偏好存于 `localStorage` 的 `planit.outlineColumnWidths`，不进项目文件、
不进撤销栈。
