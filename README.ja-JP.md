# Planit

OmniPlan のウェブ版を目指す、**依存関係駆動のスケジューリング**を核とする
ガントチャート型プロジェクト管理ツール。タスク・依存関係・カレンダー・リソースの
どれを変更してもチェーン全体が自動で再計算され、クリティカルパスはリアルタイムに
ハイライトされ、リソースの過負荷は自動で平準化され、すべての操作は取り消せます。
データはブラウザ内に保存され、サーバーは不要です。

## 機能詳説

### タスクとスケジューリング

- **タスクツリー**：サマリータスク / サブタスク / マイルストーンの 3 層構造。
  サマリーの日付はボトムアップで自動集計。タスクの種別（葉かグループか）は
  構造から自動同期するため「子を持つのに葉のまま」という不整合データは発生しません
- **2 つのスケジューリング方式**：
  - **自動** —— エンジンが依存関係と制約から解を求める。各タスクには
    **開始 / 終了の対になる制約**（開始以降 / 開始以前 / 終了以降 / 終了以前）を
    それぞれ 1 つずつ設定可能
  - **手動** —— 期間を直接固定。依存関係・制約・リソース平準化のいずれにも
    動かされません。依存関係が手動タスクに突き当たった場合は、黙ってずらすのではなく
    衝突として正直に報告します
- **タスク単位の ASAP / ALAP**：実行可能ウィンドウ内で早く取るか遅く取るかを
  選べます。プロジェクト全体は順方向（開始日から）または逆方向（期限日から遡る。
  期限なしの場合は順方向の完了日にフォールバック）でスケジュール可能
- **ドラッグでスケジューリング**：バーのドラッグで移動、左ハンドルで開始日、
  右ハンドルで工期を変更。ドロップ先は自動的に営業日にスナップ。ドラッグした
  タスクは手動スケジューリングに切り替わり、見たままが得られます
- **マイルストーン**：工期ゼロの時点。依存関係を付けられ、平準化で遅らせることも可能

### 依存関係

- **4 種類の依存タイプ**：FS（完了→開始）/ SS（開始→開始）/ FF（完了→完了）/
  SF（開始→完了）。ガントチャート上でタスクバーの端点から直接ドラッグして作成
- **ラグ（遅延）は 3 単位**：営業日 / 経過日数（週末・祝日をまたぐ）/
  前置タスク工期に対するパーセント。いずれも負値（リードタイム）可
- 循環は作成時に即座に拒否され（サイクル検出）、解決時まで放置されません
- 実現不可能な依存関係（手動タスクに突き当たるなど）は衝突リストで正直に報告。
  黙って調整することはありません

### CPM エンジンとクリティカルパス

- 完全な **クリティカルパス法（CPM）**：順方向計算（最早日）、逆方向計算（最遅日）、
  トータルフロート / フリーフロート
- **何を変更しても全体が再計算**：工期・依存関係・制約・カレンダー・リソース割り当て、
  どれか 1 つ変われば再ソルブが走ります
- **リアルタイムのクリティカルパス**：フロートゼロのチェーンがガントチャートで
  一目で分かります
- 実現不可能なスケジュール（負のフロート）は衝突として正直に報告され、
  何営業日足りないかも示されます
- ソルブは **Web Worker** 上で実行：10,000 タスクのプロジェクトでもソルブ中は
  UI が 60fps を維持。ステータスバーに「計算中」インジケーターが出ます
  （チラつき防止のため 300ms 遅延表示）

### 営業日カレンダー

- 各プロジェクトに**設定可能なカレンダー**：曜日の営業日設定 + 任意の日付の
  休日例外
- 例外は**1 日単位でも期間単位でも**追加 / 削除可能（期間はコマンド層で日ごとに
  展開されるため、1 回の取り消しで全部戻ります）
- **月次カレンダービュー**：営業日 / 非営業日 / 例外日の 3 状態着色。
  日付をクリックして切替
- リソースには**独立したカレンダー**（`calendarId`）を設定可能。
  未設定ならプロジェクトのデフォルト
- カレンダーを変えると即座に全体が再計算 —— すべてのスケジュール・負荷・
  出来高が追従します

### リソースと工作量

- **4 種類のリソース**：スタッフ / 設備 / 資材 / グループ（グループはネスト可、
  パネルはグループごとに折りたたみ）
- リソースごとに設定可能：**稼働率**（例：半人前 50%）、**効率**、
  **稼働可能期間**（入社日 / 賃借期間）、**コスト**（使用ごと + 時間単価）
- **割り当ては 2 つの対称な入口**：タスクパネルの「このタスクに誰が」、
  リソースパネルの「この人はどのタスクに」—— 同じデータ、同じコマンド。
  どちらから編集しても同じ 1 レコードです
- **2 つの工作量モデル**：
  - 固定期間：人を増やすと工作量が増え、工期は変わらない
  - **固定工作量**：人を増やすと実際に工期が縮みます（5 人日を 2 人で → 3 営業日）
- アウトラインとパネルにはタスク / リソースごとの派生合計（総使用回数・総時間・
  総コスト）が表示されます

### リソース平準化

- 同じリソースが同じ日に稼働率 100% を超えて割り当てられた場合、エンジンが
  **フロートを使ってタスクを後ろへずらし**、負荷が 100% に収まるか
  フロートが尽きるまで調整します
- **優先度が譲る順を決めます**：優先度の高いタスクが先にリソースを確保。
  固定されたタスク（手動スケジューリング / 制約付き）は一切動きません
- 手動設定の `delay`（最低繰り延べ量）は遵守されます（フロート上限でクランプ）
- **解消できない過負荷は正直に報告**（どのリソースが、どの日で、負荷いくつ）——
  「平準化済み」と嘘をつきません
- リソースビューのタイムラインで**過負荷をハイライト**。誰がどの日に
  二重 bookings されているか一目で分かります
- 平準化もただのコマンド —— **取り消せます**

### ベースラインと出来高管理（EVA）

- **複数のベースラインスナップショット**：いつでも全体のスナップショットを撮影、
  複数を保持、比較対象の切り替えは自由
- **スケジュール差異**：各タスクにベースラインの開始 / 終了と現在のスケジュールの
  営業日差（正 = 遅れ）を表示
- **出来高**：BAC / EV / PV / SV はコストと進捗からエンジンが統一的に導出。
  UI で再計算しません
- `statusDate`（基準日）+ 有効なベースラインを設定すれば PV / SV が計算できます

### ビュー

- **ガントビュー**：タスクバー、依存ライン（4 タイプの端点セマンティクス）、
  クリティカルパスのハイライト、非営業日の網掛け、ドラッグによるスケジューリング
- **アウトラインビュー**：タスクツリーを表形式で。**27 列のレジストリ**
 （開始 / 終了 / フロート / 担当 / コスト / 差異……）、ヘッダーの右クリックで
  表示設定、列幅のドラッグ調整（ダブルクリックでリセット）、設定は永続化
- **カレンダービュー / リソースビュー**：ガント・アウトラインと合わせて
  4 択のビュー切替
- **2 タブの Inspector**（タスク / プロジェクト）：タスク情報・スケジューリング・
  制約・依存関係・割り当て・ベースライン・出来高を 7 つの折りたたみグループで

### データ・取り消し・多言語対応

- **コマンドモデル**：データ変更の唯一の入口はコマンド。UI は dispatch するだけ
  で、データを直接書き換えません
- **完全な取り消し / やり直し**：Immer が正方向 / 逆方向のパッチを自動生成し、
  双方向スタックから再生。ドラッグ 1 回 = 取り消し 1 件（半歩戻りはありません）
- **自動保存**：IndexedDB にデバウン保存。リロードしても失われません。
  スキーマバージョンは**ホップ単位で移行**されるため、古いセーブは常に開けます
- **3 言語 UI**：中文 / English / 日本語を随時切替可能。すべての文案
  （取り消しメッセージを含む）が完全翻訳されます

## 開発

```bash
pnpm install
pnpm dev        # 開発サーバー（ポート 5174。Playwright の e2e も同じポート）
pnpm test       # 単体テスト（vitest）
pnpm typecheck  # 型チェック
pnpm build      # 本番ビルド
pnpm e2e        # e2e 検収（Playwright。初回は pnpm exec playwright install chromium が必要）
```

`scripts/` は開発補助スクリプトで、ビルド成果物には入りません：

- `seedLargeProject.ts` —— 1,000 タスクのストレステスト用プロジェクトを生成
 （`perf.spec.ts` で使用）。
- `importOmniPlan.py` —— 実際の OmniPlan ドキュメント（`.oplx`）を planit の
  `Project` JSON に変換（`schemaVersion` は現在の `SCHEMA_VERSION` と一致）。
  実データでスケジューリングエンジンを実測するためのもの。純粋な標準ライブラリのみ：

  ```bash
  python3 scripts/importOmniPlan.py path/to/xxx.oplx -o out.json
  ```

  インポートは**片方向かつ非可逆**です：OmniPlan の平準化結果（`leveled-start`）は
  持ち越されず、planit は自分の CPM + 平準化で再計算します —— 両者の日の差こそが
  実測で観察すべきものです。

## アーキテクチャ

```
View  (React + Mantine)    ← コマンドを dispatch するだけ、store を直接書かない
  ↓
Command (コマンドレジストリ)  ← すべてのデータ変更の唯一の入口
  ↓
Store  (Zustand + Immer)   ← コマンド + 正/逆パッチの双方向スタック
  ↓
Domain (純粋 TypeScript)   ← モデル / カレンダー / CPM ソルバー、React 依存ゼロ
  ↓
Persist (IndexedDB)        ← デバウン自動保存
```

スケジューリングエンジン（`src/domain/scheduler`）は純粋関数で、UI なしで
単体テスト可能 —— スケジュールの正しさは単体テストで保証され、UI は
「操作後にデータが正しいか」だけを検証します。再ソルブは Web Worker で
非同期に実行され、メインスレッドは描画に専念します。

OmniPlan 4 との**ルール整合**（依存変換・制約セマンティクス・リソース平準化）は、
実際の `.oplx` ドキュメントの整数日・競合なしサブセットによるパリティ回帰
（`src/domain/scheduler/omniplan/`）で検証されています。

## UI 層の 2 つの取り決め

**Mantine と自作の境界**：ツールバー・フォーム・ポップオーバー・レイアウト素片は
Mantine。ガントチャート領域（目盛り・グリッド・タスクバー・依存ライン・
タスクツリー行）は SCSS Modules + 絶対配置 + SVG で自作。これらの領域は
ピクセル単位の制御と仮想スクロールが必要で、コンポーネントライブラリは邪魔です。

**i18n**：ユーザーに見えるすべての文案は `t()` を通ります。コマンドの `label`
フィールドには i18n キー（例：`commands.task.create`）を格納し、UI が取り消し
メッセージを描画する時に初めて翻訳します —— コマンド層は言語非依存のままです。

## エンドツーエンド検収（e2e/）

かつての UI 検収は使い捨ての `browser_evaluate` アサーションでした。
`e2e/` はそれを再実行可能な Playwright テストとして固定化しました：

- `regression.spec.ts` —— 実際に発生した 6 種類の微妙な欠陥（行揃え、sticky 左列、
  接続ハンドル / リサイズグリップのクリック可能性、依存ラインの端点、ドラッグ中の
  store 不変、網掛けのカレンダー追従）。各項目は**実装非依存**の期待値
 （DOM ジオメトリまたは手計算の日付）を使い、欠陥を再導入して実際に赤くなる
  ことも検証済み。
- `acceptance.spec.ts` —— 設計ドキュメントの検収基準のうち自動化可能な部分。
- `perf.spec.ts` —— 大規模プロジェクトのストレステスト
 （スクロールフレームレート、カレンダー変更の同期ブロッキング）。
- `known-limitations.spec.ts` —— 後述の「既知の制限」のキャラクタリゼーション
  テスト。修正するとすぐ赤くなります。

```bash
pnpm e2e                                  # 全部
pnpm e2e regression.spec.ts               # 回帰のみ
pnpm e2e -g "底纹跟随用户日历"             # タイトルでフィルタ
```

## 既知の制限

> **注意**：以下の 3 つの制限にはそれぞれキャラクタリゼーションテストがあります。
> どれかを修正する際は、対応するテストと本節の該当項目を同じ変更で削除して
> ください —— さもないとテストが赤くなりますが、それは**想定内**です。

3 つとも実測済み・再現可能（`e2e/perf.spec.ts` と `e2e/known-limitations.spec.ts`）
で、意図的に未処理としています。

### 1. 大規模プロジェクトでカレンダー変更時の再描画ストール

**ソルブ自体はもうボトルネックではありません**：エンジンは Web Worker 上で
動き、10k タスクでメインスレッドのブロッキングは 797ms から ~40ms に低下。
ソルブ中も UI は 60fps を維持します（ROADMAP の「排期引擎性能」節を参照）。

**残るストールは再描画で、カレンダー変更時にのみ発生**（10,000 タスク、
本番ビルド実測）：

| 操作 | メインスレッド最大フレーム間隔 |
|---|---|
| タスク名変更（タイムライン再構築なし） | **17ms** ✅ |
| **カレンダー変更**（ガントがタイムライン + 網掛けを再構築） | **300ms** ❌ |

原因（1,000 タスク档の分解、ローカル headless Chromium 実測）：

| 部分 | 時間 |
|---|---|
| `solve()` 純ソルブ | ≈ 16ms |
| store 側の同期更新 + 強制リフロー | ≈ 17ms |
| **残り ≈ 190ms：`ProjectView` の再描画** | |
| ↳ うち非営業日網掛け | ≈ 97ms |
| ↳ その他（全行のジオメトリ memo + タイムライン） | ≈ 97ms |

1,000 ノードの長いチェーンはタイムラインを約 4,200 日に引き伸ばし、
「非営業日の網掛け」だけで **1,200 個の DOM ノード**を生みます —— カレンダーを
一時的に「毎日営業日」にするとストールは直ちに ≈ 113ms まで下がります。
store 側自体は軽い（ソルブは十数ミリ秒）。

**結論**：既知のパフォーマンス天井で、未最適化。今後の方向：網掛けの canvas /
単一グラデーション化、`rectByTaskId` とタイムラインの可視範囲シャーディング、
長チェーンでの `overscan` 低減。

> 以前のベンチマーク（別マシン / 別プロジェクト形状）では 1,000 タスクで
> 約 114ms、2,000 タスクで約 215ms。絶対値はマシンとタイムライン幅で変わりますが、
> オーダーは**数百ミリ秒**です。
>
> ⚠️ この計測は**本番ビルドで行うこと**：React 開発モードのオーバーヘッドは
> 10k 規模ではレンダリング時間の大半を占めます（同一操作で dev 746ms vs 本番 17ms）。
> dev の数字で判断すると最適化の方向を誤ります。

### 2. プロジェクト開始前のスケジュールはタイムライン原点の左に描かれる

手動スケジューリングや負のラグでタスクの開始日が `project.startDate` より
**早くなる**と、バーはタイムライン原点の左（`left` が負）に落ち、sticky 左列に
覆われます。

例：プロジェクト開始 `2026-03-02`。工期 3 のタスクを手動で `2026-03-03` 終了に
固定すると、開始日は `2026-02-27` に逆算されます —— 原点より 3 自然日早く、
バーは `x = -96px` に描かれます。

これは**以前から存在する**挙動です：タイムライン原点は `project.startDate` に
固定されており、それより早いスケジュールのタスクは覆われます。
`e2e/known-limitations.spec.ts` が現在の挙動を証拠として固定しています。

### 3. 列幅をキーボードで調整できない

アウトラインビューの列幅はヘッダー境界線のマウス / タッチドラッグでのみ変更可能
（ダブルクリックで 1 列リセット）。キーボードからの入口はありません
（ハンドルは `tabindex` のない `role="separator"` の div です）。幅の設定は
`localStorage` の `planit.outlineColumnWidths` に保存され、プロジェクトファイルや
取り消しスタックには入りません。

## ロードマップとドキュメント

v0.1 → v1.0 のバージョンシリーズはすべて納品済み（タスクツリーと依存スケジューリング
→ 双ビューと列システム → Inspector → リソースと工作量 → リソース平準化 →
カレンダー / リソースビュー → 日時精度 → ベースラインと出来高）。その後
エンジン v2 の書き直し（ラグ 3 単位、手動スケジューリング、OmniPlan パリティ、
Web Worker 化と大規模パフォーマンス改善）を完了しました。

- [`docs/superpowers/ROADMAP.md`](docs/superpowers/ROADMAP.md) ——
  バージョンロードマップと実測パフォーマンスデータ

  セッション間ハンドオフ（状態 / キュー / 規律）
